# Nexus Shell

A React component library for building IDE-style application shells — menu bar,
activity bar, sidebar, docking workspace, terminal, chat pane and status bar.

## Install

```bash
npm install nexus-shell
```

Import the stylesheet once, in your app entry:

```ts
import 'nexus-shell/style.css';
```

React 19 is a peer dependency; bring your own.

## Start with the shell

An application built on this library starts with `ShellLayout` and grows by
registering things into it. That is the intended path, and the one the rest of
these docs assume.

```tsx
import { initializeShell, ShellLayout, componentRegistry, AppTitle } from 'nexus-shell';
import 'nexus-shell/style.css';

componentRegistry.register('editor', Editor);

initializeShell({
  panels: [{ id: 'files', label: 'Explorer', icon: Files, component: FileTree }],
  commands: [{ id: 'file.save', label: 'File: Save', keybinding: 'Control+s', execute: save }],
  menus: { File: [{ id: 'save', label: 'Save', commandId: 'file.save' }] },
  statusBar: [{ id: 'branch', label: 'main', alignment: 'left' }],
});

createRoot(el).render(<ShellLayout title={<AppTitle title="Acme Studio" />} />);
```

That is a working IDE: dockable tabs, a command palette on `Cmd/Ctrl+Shift+P`, a
terminal, a themable chrome. See [ShellLayout](/docs/layout-shelllayout--docs)
for the full frame, live.

## How an app grows

You add capability by **registering** it, not by restructuring the layout.

| To add | Do this |
| :-- | :-- |
| A new view or tab | `componentRegistry.register(id, Component)`, then open it with `useLayoutStore().addTab(id, title)` |
| An action or hotkey | `commandRegistry.registerCommand({ id, label, keybinding, execute })` — it appears in the palette automatically |
| A menu entry | Add an item with that `commandId` to `menus` |
| A sidebar panel | Add it to `panels`; it becomes an activity bar icon |
| A status bar item | `useStatusBarStore.getState().addWidget(...)` |
| A dialog from anywhere | `await useModalStore.getState().openConfirm('Sure?')` |

None of these require touching the shell, which is what lets plugins and
distant code contribute to it. See
[Registry Architecture](/docs/guides-registry-architecture-ioc--docs).

## The components underneath

Everything the shell is assembled from is exported too. Those components are
pure and prop-driven — no global state, no registry lookups — and they are the
**escape hatch**, not the starting point.

Reach for them when you are:

- embedding one piece into an application you already have,
- building a frame the shell can't express,
- or rendering the same component twice with different data.

```tsx
import { StatusBar } from 'nexus-shell';

<StatusBar widgets={[{ id: 'branch', label: 'main', alignment: 'left' }]} />;
```

Between the shell and those components sit the `Connected*` variants — `ConnectedStatusBar`,
`ConnectedMenuBar`, and so on. Each binds one component to its store.
`ShellLayout` is built entirely out of them, so you can rearrange the shell's
own parts while keeping its behaviour.

## Why the components are pure

A component that reads a global store can't be configured by its caller, can't
be rendered twice with different data, and can't be documented — its props table
is empty because it has no props.

Keeping presentation and wiring in separate layers is what makes the pages in
this Storybook useful: every control you see maps to a real prop. It is an
implementation discipline that pays off in documentation, not an instruction to
assemble the shell by hand.

## Theming

Four themes ship in the stylesheet: `theme-light`, `theme-dark`, `theme-gt`
(Georgia Tech) and `theme-tamu` (Texas A&M).
Colors are CSS custom properties scoped to those classes, so theming is a class
on an ancestor element, not a React context.

Use the **Theme** toolbar control above to switch any story between them. See
[Theming](/docs/guides-theming-styling--docs) for the full token list.
